# CI-only requirements. Use requirements.txt for local development.
#
# WHY THIS FILE EXISTS, measured rather than assumed:
# putting the jobcore git URL in requirements.txt CLOBBERS a local editable
# install. Verified on a clean venv 2026-08-20 -- after `pip install -e
# ../jobcore`, running `pip install -r <file with the git URL>` printed
# "Attempting uninstall: jobcore / Successfully uninstalled", the
# "Editable project location" line disappeared, and the __editable__ shim was
# replaced by a real jobcore/ directory. Reproduced twice. pip prints no
# "Requirement already satisfied" line for a direct-URL requirement, so the
# clobber is silent unless you go looking.
#
# Local iteration on jobcore matters more than CI convenience, so CI is the
# side that installs from git and requirements.txt stays editable-friendly.
#
# LOCAL DEVELOPERS: do not use this file. See requirements.txt.

-r requirements.txt

# Pinned to an exact commit, not @master. naukri's tests assert specific
# taxonomy behaviour -- tests/test_search_impressions_invariants.py needs the
# typographic-quote folding added in jobcore 3f2f742, which this commit contains
# -- so a moving branch would let a commit in another repo turn this repo's CI
# red with no change here.
# Bumping this line is the visible, reviewable way to adopt a jobcore change.
#
# BUMP DISCIPLINE, learned the expensive way (2026-08-21): this pin is also the
# way to turn CI red with no change in jobcore. naukri_server/policy.py started
# importing `jobcore.policy` -- added in jobcore 2cddb0e -- while this line
# still said d1d44bb, the commit BEFORE it. Two pushes went red with 37
# collection errors and `ModuleNotFoundError: No module named 'jobcore.policy'`
# before anyone looked at Actions. A local venv cannot catch this: it has
# jobcore installed editable from ../jobcore and therefore always has the new
# module. THE RULE: any commit here that adds a `from jobcore...` import of
# something new bumps this line in the SAME commit, and the bump is verified by
# installing this file into a throwaway venv -- not by running the local suite.
#
# AND IT HAPPENED AGAIN, 2026-08-22, with the rule already written above.
# Commit 8a8f596 added `naukri_server/buildinfo.py` (imports `jobcore.buildinfo`)
# and made `policy.display_path` delegate to `jobcore.paths` -- two modules that
# do not exist at 16ae934. `git ls-tree --name-only 16ae934 src/jobcore/` lists
# seven files and neither of those is among them, so CI would have installed the
# pin and died at COLLECTION with `ModuleNotFoundError: No module named
# 'jobcore.buildinfo'`, with every local run staying green for exactly the
# reason the paragraph above gives. The follow-up commit then also needed
# `Loaded.report(display=...)`, `Loaded.status_for`, `Loaded.known_paths` and
# `jobcore.paths.relativise_known`, all of which arrived in 0f557eb.
#
# So this is not "the rule was unclear" -- the rule was written down and the
# bump was still forgotten, because nothing MECHANICAL checked it.
# tests/test_jobcore_pin.py is that check: it reads this line and asserts every
# `jobcore.<module>` the package imports exists in the pinned tree. It runs off
# the local ../jobcore clone and skips when that clone is absent, so it catches
# the mistake before a push rather than after a CI round trip.
#
# SECOND RULE, same day: PIN A COMMIT WHOSE OWN CI IS GREEN. 0f557eb carried
# everything needed and was the obvious target, but its jobcore CI run was RED.
# Pinning a red commit makes a green naukri CI mean nothing -- naukri would be
# certifying itself against a dependency nobody had certified.
#
# THIRD RULE, and the reason the check above now reads NAMES and not just
# modules: a pin can be new enough for the MODULE and too old for the ATTRIBUTE.
# Measured across the three commits this file has pointed at:
#
#     16ae934 : buildinfo.py present=0  def self_stamp=n/a
#     d1720c3 : buildinfo.py present=1  def self_stamp=0
#     998baf1 : buildinfo.py present=1  def self_stamp=1
#
# `naukri_server/buildinfo.py` now calls `jobcore.buildinfo.self_stamp()`, which
# d1720c3 does not have -- CI would have died with `AttributeError: module
# 'jobcore.buildinfo' has no attribute 'self_stamp'`, one commit after fixing
# the ModuleNotFoundError. A sibling repo hit exactly that today.
#
# 998baf1 is jobcore master, CI-verified green, a descendant of d1720c3, and
# carries `self_stamp`, the `version` field on BuildStamp, and
